## Hardware meaning

`0x1F8010F0` is `DPCR`: four bits per DMA channel — bits 0–2 priority, bit 3
enable. Three separate retail pointers hold this address
(`D_8009DD1C`, `D_8009DEE4`, `D_8009EEB4`); they are distinct variables, so
each gets its own name.

Which DMA channel the game enables through this pointer is not established by
the code alone: the unit only sets bit `0x800` and bit `0x8000000` with a
read-modify-write. Bit `0x800` is within nibble 2 (bits 8–11), i.e. the enable
bit of the channel that nibble controls. **Uncertain:** the mapping of that
nibble to a channel number is assumed from public documentation, not proven
from this unit; the name therefore says "GPU path" (the calling context) and
not a channel number.

## Correct C type

`u32 *` in all four users (non-volatile; the units were matched that way).

## Users

* `func_8009415C` — sets bit `0x8000000` together with a transfer setup.
* `func_80094F4C` — sets bit `0x800` before starting the GPU transfer
  (`*gDma2ChannelCtrlPtr = 0x401`).
* `func_8009509C`, `func_8009520C` — same enable path in their transfer
  routines.

`analysis/refs.json` records the slot loads; the slot itself is never written.

## Accessing the variable vs. the register

```c
*gDmaControlGpuPtr |= 0x800;          /* read-modify-write in DPCR */
u32 addr = (u32)gDmaControlGpuPtr;    /* 0x1F8010F0, no side effect */
```

## C integration status

Renamed from `D_8009DEE4` to `gDmaControlGpuPtr` in its four C users; the
retail symbol is kept with `__asm__("D_8009DEE4")`. No object is defined, the
retail word stays in `asm/us/main.s`, and the affected units still compile to
the exact retail bytes (SHA-256 compared before and after the rename).
