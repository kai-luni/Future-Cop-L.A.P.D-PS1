# D_8009C7A4 — serial port 0 receive data pointer

## Identity

| item | value |
| --- | --- |
| retail symbol | `D_8009C7A4` |
| C name | `gSio0RxDataPtr` |
| slot address | `0x8009C7A4` (4 bytes, writable, inside the payload's `.text`) |
| initial value | `0x1F801040` |
| points at | serial port 0 data register (JOY_DATA), read side |
| assembler label | `SIO0_RX_DATA_ASM` in `include/game/sio_globals.h` |

## Retail evidence

`asm/us/main.s`:

```
dlabel D_8009C7A4
    /* 8CFA4 8009C7A4 4010801F */ .word 0x1F801040
```

File offset `0x8CFA4` of `SLUS_007.39` holds `40 10 80 1F`, i.e. `0x1F801040`.
Three other slots hold the same address (`D_8009C7C0`, `D_8009C804`,
`D_8009C78C`); they are separate variables and are named by their access role.

## Hardware meaning

`0x1F801040` is `JOY_DATA`. This unit only reads it — `*gSio0RxDataPtr` returns
the byte the controller or memory card sent — which is why the name says "receive
data". Reading the register clears the receive flag in `JOY_STAT`.

## Correct C type

`volatile u8 *` (the pointee must be volatile: each read consumes a byte).

## Users

* `func_8008BA34` — appends the received byte to the caller's buffer
  (`arg0->unk3C[arg0->unk44++] = *ptr`).

`analysis/refs.json` records the slot loads; the slot itself is never written.

## Accessing the variable vs. the register

```c
u8 byte = *gSio0RxDataPtr;      /* consumes one received byte */
u32 addr = (u32)gSio0RxDataPtr; /* 0x1F801040, no effect      */
```

## C integration status

Renamed from `D_8009C7A4` to `gSio0RxDataPtr` in its single user; the retail
symbol is kept with `__asm__("D_8009C7A4")`. No object is defined, the retail
word stays in `asm/us/main.s`, and the unit still compiles to the exact retail
bytes (SHA-256 compared before and after the rename).
